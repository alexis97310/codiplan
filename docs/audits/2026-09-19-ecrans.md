# AUDIT — les huit écrans contre la maquette

**Ce document ne modifie aucun fichier de produit.** Il mesure, il ne corrige pas (règle 1 de la commande d'audit).

## Ce qui a été mesuré, et comment — à lire avant tout le reste

**Le site déployé (https://codiplan.vercel.app) est resté injoignable depuis cette session.** Le proxy sortant de cet environnement refuse la connexion (`EGRESS_BLOCKED` / `CONNECT tunnel failed, response 403`) vers `codiplan.vercel.app` — et vers `vercel.com` en général, ce qui exclut un blocage propre au seul nom de domaine du produit. La base hébergée (Neon) est, elle, documentée comme injoignable depuis une session cloud par le dépôt lui-même : `docs/mise-en-ligne.md` (~ligne 158) écrit noir sur blanc que « le proxy sortant ne relaie pas le TCP, la base y est injoignable — P1001 » ; mesuré ici aussi, `psql "$DATABASE_URL"` expire sans répondre.

Pour respecter malgré tout la consigne « ouvre le site en ligne, ne te contente pas de lire la source », l'application a été **construite et exécutée en local**, sur le commit exact de cette branche (issu de `main`), avec un PostgreSQL 16 local et jetable (`scripts/postgres-jetable.sh`), migrée (`pnpm db:deploy`) et semée (`pnpm db:seed` — deux sociétés de démonstration, XPF et EUR, I9). Un compte de démonstration (`direction@codima.test`) a reçu un mot de passe via le geste d'amorçage documenté (`scripts/amorcage-premier-compte.mts --reemettre`), et les captures ont été prises avec l'outil déjà présent dans le dépôt (`scripts/captures.mts`), complété pour deux écrans qu'il ne couvrait pas encore (`tableau-de-bord`, `interventions`) via une copie temporaire jamais commitée.

**Ce que cette substitution vaut, et ce qu'elle ne vaut pas :** c'est le même code, au même commit, exécuté réellement — pas une lecture de source. Ce n'est PAS la même base de données (démonstration locale plutôt que base hébergée), donc tout ce qui dépend du VOLUME ou du CONTENU exact des données réelles de production (nombre de lignes, état d'un import passé, etc.) n'est pas mesuré ici à l'identique — seulement la disposition et le comportement du code, qui ne dépendent pas de l'hébergeur.

**Le portail client (8ᵉ écran) fait exception : aucune capture authentifiée n'a pu en être prise, ni ici ni ailleurs aujourd'hui.** Voir sa section dédiée — ce n'est pas une limite de cette session, c'est un fait du produit, déjà documenté dans `scripts/captures.mts`.

Captures déposées dans `docs/audits/2026-09-19/` :
- `maquette--<écran>.png` — la maquette de référence, rendue localement (fichier statique, aucun réseau requis), à 1280 px.
- `vivant--<écran>--1280.png` — l'application réelle, construite et exécutée localement comme décrit ci-dessus, à 1280 px (absent pour `portail`, voir sa section).

Le module porte trois fonctions : `recevoir` (dépose un fichier au bac de réception, avec déduplication par empreinte), `classer` (rattache un reçu du bac à une cible nommée — machine ou modèle), `ecarter` (rejette un reçu sans le classer). Recherche exhaustive de leurs appelants dans tout le dépôt (`app/`, hors tests) :

- `recevoir`, `classer`, `ecarter` : **aucun appelant nulle part dans `app/`.** Seuls les tests d'isolation (`tests/isolation/bac-de-reception.test.ts`, `document.test.ts`) les invoquent.
- Le seul import de `lib/documents/depot` dans `app/` est `documentsDeLaMachine` (lecture seule), utilisé par `app/(back-office)/parc/[id]/page.tsx` pour AFFICHER les documents déjà présents en base — jamais pour en ajouter.

**Conclusion : aucune route API, aucun formulaire, aucun bouton n'existe nulle part dans le dépôt pour déposer un document.** La fiche machine (`/parc/[id]`) affiche une carte « Documents » (lecture seule, tableau) avec, sous le tableau, ce texte exact, déjà écrit dans le code : *« Les fiches sont en base ; les octets attendent le stockage d'objets, qui n'a pas encore d'appelant (L8-05). »* (`lib/i18n/fr.ts`, clé `machine.documents.sans_octets`).

### Le champ `document.objet_cle` — qui le remplit

Recherche de tous les points d'écriture de `objet_cle` dans `lib/` : le champ est **fourni en paramètre** par l'appelant de `recevoir` (`lib/documents/saisie.ts`, validé par Zod comme texte non vide), jamais **fabriqué** par le module lui-même. Le commentaire d'en-tête de `lib/documents/depot.ts` le dit explicitement : *« Aucun transport d'octets. Le module de stockage n'existe pas, faute d'appelant : `objet_cle` est fournie, jamais fabriquée. »* Aucun module `lib/stockage/*` ou équivalent (le S3-compatible imposé par le §2 du CLAUDE.md) n'existe dans le dépôt — vérifié par recherche de fichiers.

### Ce qui manque précisément

**Les deux manquent, et ils manquent dans cet ordre de dépendance : le stockage d'abord, l'écran ensuite.**

1. **Le stockage** (le fournisseur S3-compatible imposé par le §2 du CLAUDE.md) n'existe pas du tout dans le dépôt. C'est la cause racine : sans lui, aucun appelant ne peut jamais obtenir un `objet_cle` réel, puisque ce champ n'est jamais fabriqué en interne.
2. **L'écran** (un bouton « Ajouter un document » sur la fiche machine, avec sélection de fichier, cible de classement, visibilité) n'existe pas non plus — mais c'est une conséquence directe du point 1, pas un manque indépendant.

**Un écran seul, sans stockage, n'aurait pas de sens** : `recevoir` exige un `objet_cle` déjà valide (texte non vide, validé par Zod) — sans un fournisseur de stockage qui accepte l'upload et renvoie une clé d'objet, aucun formulaire ne pourrait produire cette valeur autrement qu'en l'inventant (ce que le dépôt interdit explicitement dans son propre commentaire : « aucun transport d'octets »). Construire l'écran d'abord obligerait soit à un stockage factice temporaire, soit à un formulaire qui ne fonctionnerait pas — les deux sont désignés comme des raccourcis à ne pas prendre par l'esprit du §9 du CLAUDE.md (« le silence a la forme du succès »).

**Ce que le dépôt sait déjà faire, en revanche** : `classer` et `ecarter` sont écrits et testés — une fois un reçu présent au bac (par n'importe quel moyen de dépôt), le rattachement à une machine ou à un modèle fonctionne. C'est bien la **réception** (l'upload proprement dit, donc le stockage) qui est le chaînon manquant, pas le rattachement métier.

### Nature de l'écart

C'est un écart de **DONNÉES/INFRASTRUCTURE**, pas de design : aucune disposition de maquette n'est en cause ici (aucune des huit fonctions étudiées plus haut ne dessine un formulaire d'ajout de document — le point d'Alexis porte sur une fonctionnalité absente du produit, indépendamment de la maquette). Coût estimé : **élevé** — nécessite de choisir et intégrer un fournisseur de stockage S3-compatible (une dépendance externe payante potentielle, ce qui est un point d'arrêt explicite du §8 du CLAUDE.md : « l'ajout d'une dépendance lourde ou d'un service externe payant »), avant même d'écrire l'écran de dépôt.

## Améliorations proposées (hors écarts à la maquette)

**Un écart se mesure contre la maquette ; une amélioration s'argumente sur son propre mérite. Ce qui suit n'est pas mesuré contre `docs/maquette/codiplan-maquette-complete.html` — ce sont des avis, à discuter, jamais des faits constatés.**

1. **Badge de synthèse compatible D88 sur `/vgp`.** La colonne « État » de la maquette a disparu à raison (un badge « Conforme » violerait D88), mais rien ne remplace aujourd'hui le repère visuel d'un coup d'œil. Un badge codant l'ÉTAT DE L'INFORMATION (« Hors registre » / « Sans information » / « Information reçue ») plutôt qu'un verdict de conformité respecterait D88 tout en redonnant une lecture rapide de la liste. Coût moyen : un design de badge + un petit changement de `LigneDeRegistre`, aucune nouvelle donnée à calculer.

2. **Recherche élargie sur `/interventions`.** La recherche actuelle ne porte que sur le client et le site (choix assumé, AT-07). Beaucoup d'utilisateurs chercheront par référence d'intervention (`INT-2026-…`) — cette référence existe déjà en colonne. Étendre la recherche à la référence serait un gain d'usage à faible risque, sans toucher au périmètre cloisonné. Coût faible à moyen (selon si un point d'arrêt §8 est jugé nécessaire pour rouvrir AT-07).

3. **Restituer la priorité et la machine sur le tableau `/interventions`.** Les deux données existent déjà côté serveur (`priorite`, triée ; `machines`, jointes) mais ne sont pas affichées. C'est la plus rentable des améliorations possibles ici : aucune nouvelle donnée à produire, seulement à restituer. Coût faible pour la priorité (un badge sur un enum déjà lu), moyen pour la machine (choix d'affichage à trancher pour le cas multi-machines).

4. **Fil d'ariane inter-écrans sur `/imports`.** Le flux réel (dépôt → rapport → application → résultat) est piloté par le statut du lot et traverse deux routes, sans aucun repère visuel de progression. Un indicateur discret dérivé du statut réel (pas un simple copier-coller de l'assistant à 4 pas de la maquette, qui suppose un seul écran) aiderait un utilisateur à savoir où il en est sans devoir déduire l'étape de l'URL. Coût moyen.

5. **Lien cliquable (téléphone/courriel) sur le bloc « Demander une intervention » du portail.** Le texte actuel renvoie à un appel téléphonique de façon purement descriptive. Un lien `tel:`/`mailto:` réel, ou un formulaire simple, réduirait la friction pour le client sans nécessiter le registre complet d'interventions (lot 8/9). Coût faible.

6. **Compteur de « demandes en attente de qualification » rendu actionnable sur le tableau de bord.** La carte existe déjà (ajout réel non prévu par la maquette) mais n'a pas été vue lors de cet audit avec un lien vers l'écran correspondant (à vérifier sur la capture réelle) — si ce n'est pas déjà le cas, un lien direct suivrait le même principe que celui déjà appliqué à « Voir le planning → ». Coût faible.

7. **Documenter dans le commentaire du fichier l'ajout du KPI « Clients sans code externe » sur le tableau de bord.** Ce n'est pas un problème d'écran mais d'hygiène de dépôt : les deux autres KPI ajoutés sont expliqués en tête de fichier (pourquoi ils existent, ce qu'ils mesurent), celui-ci ne l'est pas — cela facilite la relecture future et respecte l'esprit du §9 du CLAUDE.md (« nommer ce qu'on ne sait pas » vaut aussi pour le code qu'on écrit soi-même). Coût négligeable.
